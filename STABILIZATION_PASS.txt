# Technical Task: Build Engine Stabilization & Optimization

We need to address three stability and performance issues in the `:engine:fast` and `:toolchain:native` modules. Follow these specific instructions to implement process isolation, output streaming, and basic incrementality.

## 1. Process Isolation & Memory Headroom
The Kotlin compiler (`kotlinc`) and `D8` are memory-intensive. We must ensure they don't OOM the editor process.

*   **Modify `app/src/main/AndroidManifest.xml`**:
    *   Add `android:largeHeap="true"` to the `<application>` tag.
    *   *Note:* The long-term plan is a `:build` process via a Bound Service, but for now, provide the heap headroom for the main process.
*   **Update `app/build.gradle.kts`**:
    *   Ensure `dexOptions { javaMaxHeapSize = "4g" }` (or similar) is set if needed for the host-side build, but for the on-device engine, the `largeHeap` manifest flag is the primary lever.

## 2. Refactor `NativeToolRunner` for Streaming Output
Currently, `NativeToolRunner.run()` uses `readText()`, which loads the entire output of `aapt2` into a single `String`. This is an OOM risk for large projects.

*   **Modify `NativeToolRunner.kt`**:
    *   Change the `run` function signature to accept a `onDiagnostic: (String) -> Unit` callback or return a `Flow<String>`.
    *   Instead of `async { ... readText() }`, use `inputStream.bufferedReader().forEachLine { line -> ... }`.
    *   Ensure you still drain both `stdout` and `stderr` concurrently to prevent the process from deadlocking when the pipe buffer fills up.
*   **Update `ResourceStage.kt`**:
    *   Update the `interpret` function to handle the streaming output. It should collect diagnostics incrementally rather than waiting for the process to exit.

## 3. Basic Incrementality in `FastBuildSystem`
Currently, `BuildWorkspace.prepare()` deletes the entire build folder every time. We need to skip work if the inputs haven't changed.

*   **Modify `BuildWorkspace.kt`**:
    *   Change `prepare()` so it doesn't unconditionally delete everything. It should only clear the `generated/` and `classes/` folders if the build is "dirty".
*   **Update `FastBuildSystem.kt`**:
    *   Implement a simple "Up-to-Date" check. Compare the `lastModified` timestamp of the `outputApk` against the latest `lastModified` of the `src/` and `res/` directories.
    *   If the `res/` directory hasn't changed since the `linkedApk` was built, skip the `compile` and `link` stages.
    *   If the `src/` directory hasn't changed since the `classes.dex` was built, skip the `javac` and `dex` stages.

## 4. Verification
*   Verify that "Jump to Error" still works. Ensure `ProjectPaths.relativise` is applied to the streamed diagnostic lines.
*   Run the `:engine:fast` instrumented tests to ensure the signed APK is still valid and the build budget (< 10s) is still met.

# Building a tree-sitter grammar for this app

Established 2026-09-07, when M10 shipped JavaScript support and every `.js`
file opened as plain text.

## 1. The publisher of our grammars ships no JavaScript one

`:editor` gets its grammars as AARs from `com.itsaky.androidide.treesitter`.
Asked what it publishes, Maven Central answers:

```
tree-sitter-aidl, tree-sitter-c, tree-sitter-cpp, tree-sitter-java,
tree-sitter-json, tree-sitter-kotlin, tree-sitter-log, tree-sitter-properties,
tree-sitter-python, tree-sitter-xml
```

That is the whole list, and neither `javascript` nor `c-sharp` is on it. So the
choice was between shipping a language with no highlighting or building the
grammar, and this document is the second.

## 2. A grammar AAR is four moving parts, three of which are ours already

Unpacking `tree-sitter-json-4.3.2.aar` shows how little is in one:

- `jni/<abi>/libtree-sitter-json.so` — **12 KB**, exporting exactly
  `tree_sitter_json` and one JNI method
- `TSLanguageJson.class` — `System.loadLibrary`, a native method returning a
  pointer as a `long`, and `TSLanguage.create(name, pointer)`
- nothing else: no runtime, no queries

The runtime (`libandroid-tree-sitter.so`, 539 exported symbols) is a separate
dependency we already have, and the query is not in the AAR at all — ours are
vendored from each grammar's own repository, which
`editor/src/main/assets/treesitter/README.md` records.

`TSLanguage.create` and `TSLanguageCache.cache/get` are **public API**, so the
glue is a Kotlin object rather than a fork. `JavaScriptGrammar` is that object.

**Go through the cache.** A `TSLanguage` freed while a `TsLanguageSpec` still
refers to it takes the editor down, and the cache is how two open files share
one — the same hazard `EditorLanguages` documents for specs, one level lower.

## 3. Grammar ABI 14 is what the runtime accepts

A parser generated by a newer tree-sitter CLI declares a `LANGUAGE_VERSION` the
runtime may refuse, and the refusal is silent: the library still loads,
`TSLanguage.create` still answers, and the file renders as plain text — exactly
what it did before. tree-sitter-javascript **v0.23.1** declares 14 and works
with `android-tree-sitter` 4.3.2. That is the reason the version is pinned
rather than tracked.

`EditorHighlightTest.a_javascript_file_is_highlighted_by_the_grammar_we_build`
is what would notice: it asserts coloured spans on a real `.js` buffer, which
neither loading the library nor compiling the query proves.

## 4. Building it

`build-grammars.sh`, from a pinned tarball verified against a sha256, with the
NDK. Two ABIs, because `:app` filters to `arm64-v8a` and `x86_64`.

```
    arm64-v8a  364K
    x86_64     368K
```

Two flags are not incidental:

- `-Wl,--build-id=none -s` — the output lands **in git**, and without them a
  rebuild of identical source produces a different build id and shows as a
  371 KB diff. With them two builds are byte-identical, which is what makes
  "rerun the script" a check rather than a commit.
- `-Wl,-z,max-page-size=16384` — Android 15's 16 KB pages. A 4 KB-aligned
  library fails to load there, on a device nobody testing on API 34 has.

## 5. JSX is the same grammar and a longer query

tree-sitter-javascript parses JSX already — `jsx_element`, `jsx_opening_element`
and the rest are in its `node-types.json`. What `.jsx` needs is upstream's
`highlights-jsx.scm`, which is eight patterns written to be applied **on top of**
`highlights.scm` rather than instead of it.

tree-sitter applies one query per language, so the build script concatenates the
two into `javascriptx/` and `EditorLanguage` has a second entry pointing at the
same grammar. Adding `jsx` to JavaScript's extensions instead would highlight
those files with the query that has no idea what a tag is — which compiles, runs,
and colours nothing, the failure mode this whole document is about.

## 6. C# is buildable and deliberately not built

The same script builds it — `tree-sitter-c-sharp` v0.23.1 also declares ABI 14
— but the size is the whole argument:

| grammar | `src/parser.c` | `.so` per ABI | committed |
|---|---|---|---|
| javascript | 2.4 MB | 371 KB | 742 KB |
| c-sharp | 34 MB | 5.9 MB | 12 MB |

12 MB in git and in every APK, for a language `docs/PLAN.md` already names as
the defensible cut if M10 is ever trimmed. The app's entire committed native
payload today is 9 MB of aapt2, so this would more than double it.

The measurement is the finding. If C# highlighting is wanted, the route is a
`ToolchainComponent` beside mono's — the grammar is a file loaded by path, and
`System.loadLibrary` is the only part that would need replacing with
`System.load`.
